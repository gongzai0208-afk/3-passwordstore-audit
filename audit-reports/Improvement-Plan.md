## 1. 事实性错误（必须改，优先级最高）

### 1.1 引用了不存在的函数名

`finding_layout.md:11`：

> ...and only asscessed through the **`PasswordStore::s_password`** function...

合约里**没有**名为 `s_password` 的函数，`s_password` 是状态变量。取密码的函数是
`PasswordStore::getPassword()`。

这是全篇唯一一处「读起来通顺、但对着代码一查就穿帮」的错误。审计报告的可信度建立在「每句话都能被源码验证」
之上，这类错误会直接动摇读者对整份报告的信任。

**改法：** `only accessed through the PasswordStore::getPassword function`

### 1.2 修复代码编译不过

`finding_layout.md:96-101` 给出的缓解代码：

```javascript
if(msg.sender!=s_owner){
    revert PassWordStore_NotOwner();   // ← 编译不过
}
```

合约实际声明的 error 是 `PasswordStore__NotOwner()`（**双下划线**，`Password` 而非 `PassWord`）。
按上面这段照抄，编译器会直接报 `Undeclared identifier`。

**改法：** `revert PasswordStore__NotOwner();`

> 这类错误的杀伤力比 1.1 更大：1.1 是描述错，1.2 是**建议开发者照抄一份跑不起来的代码**。
> 建议养成习惯：报告里给出的每一段修复代码，落笔前先在本地跑一次 `forge build`。

### 1.3 命令参数拼写错误

`finding_layout.md:33`：

```bash
cast storage <ADDRESS_HERE> 1 --rcp-url http://127.0.0.1:8545
```

`--rcp-url` 应为 `--rpc-url`。照抄这条命令会报 `unexpected argument`。

### 1.4 命令块没有对应到真实部署流程

`finding_layout.md:22-27` 写的是 `make anvil` + `make deploy`，但 `make deploy` 的地址不会打印在一个显眼位置，
读者拿不到 `<ADDRESS_HERE>`。规范做法是在 PoC 里补一句「从部署输出中取 `Contract Address`」，
或者干脆给出确定性地址（例如 `0x5fbdb2315678afecb367f032d93f642f64180aa3` —— 标准 anvil 助记词下首次
`CREATE` 的地址是固定的）。

### 1.5 `[S-#]` 占位符从未填写

`finding_layout.md:60`、`104` 两处的标题仍是 `[S-#]`。`S-` 是模板的严重等级前缀，`#` 是要你填的数字。
这两条**你其实已经判断了等级**（第 2 条你正文里写 High），只是忘了回填到标题。

### 1.6 等级标题格式不统一

- `:6` 用 `[S-HIGH]`
- `:9` 用 `[S-HIGH!]`（多个感叹号，非标准）
- `:60`、`:104` 用 `[S-#]`

同一份报告里三种写法。**改法：** 统一为 `[H-1]`、`[H-2]`、`[I-1]` 这种「等级缩写 + 序号」格式 ——
这是 Code4rena / Sherlock / Cyfrin 通行的写法，也让正文里能互相交叉引用（如「详见 [H-2]」）。

## 2. 走了弯路：漏掉的发现

手写版列了 3 条。我按同一份代码逐行走查，另有 6 条**结构性缺陷**你没写，其中两条不看你反而更该写，
因为它们正是「读注释」就能发现、不需要跑代码的：

| 编号 | 你漏掉的发现 | 等级 | 为什么值得写 |
| --- | --- | --- | --- |
| I-3 | 事件名 `SetNetPassword` 拼写错误（应为 `SetNewPassword`） | 提示级 | 声明与触发点**两处都要改**，且一旦部署就改不动了（topic 哈希会变）。这类「部署即锁定」的窗口期问题，是审计里很有分量的观察。 |
| I-4 | 合约头注释用 `/*` 而非 `/**`，**整块 NatSpec 被编译器丢弃** | 提示级 | 最能体现细节功力的一条。讽刺的是：你写的第 3 条发现（`@param` 冗余）之所以存在，恰恰因为函数级注释里只有那一块用了正确的 `/**`… —— 换句话说，`/*` 那两块根本没进文档，你才没看见问题。 |
| I-5 | `SetNetPassword` 不带任何参数，链下无法观测变更 | 提示级 | 与 H-2 叠加后，「越权覆盖」在日志里也留不下痕迹。 |
| I-6 | owner 角色无法轮换 | 提示级 | 私钥泄露后无法补救；私钥丢失则 `getPassword` 永久 revert。 |
| I-7 | 接受空密码，且「清空」与「设为空」无法区分 | 提示级 | 调用者能静默清空数据。 |

> **不是要你为凑数而写。** 这 6 条我没有硬凑等级 —— 全部如实定为「提示级」，因为它们的单独后果确实有限。
> 但审计报告的专业度，很多时候恰恰体现在**能否把所有等级的问题都覆盖到**，而不是只报高危。
> 客户花钱买的是「清单的完整性」，不是「高危的数量」。

## 3. 合规报告缺失的章节

一份能被客户或竞赛平台接受的报告，除了「发现」本身，还需要下面这些**结构性章节**。手写版一个都没有：

| 章节 | 作用 | 手写版状况 |
| --- | --- | --- |
| 文档信息 / 元数据表 | 锁定受审版本、Solc 版本、链、审计日期 | ❌ 缺。**尤其缺 commit hash** |
| 免责声明 | 界定责任边界（范围外了什么、不保证什么） | ❌ 缺 |
| 风险等级标准 | 定义 High/Medium/Low 各自的判定口径 | ❌ 缺。你用了 High 这个词，但没定义它对你意味着什么 |
| 审计范围 | 哪些文件在范围内、哪些不在 | ❌ 缺（README 里本来有，后来被覆盖了 —— 见 §5.2） |
| 发现汇总表 | 一眼看到「2 高危 / 0 中危 / …」 | ❌ 缺 |
| 审计方法 | 说明你做了什么：人工走查？静态分析？写了 PoC？ | ❌ 缺 |
| 修复后验证 | 给出判定修复是否生效的测试 | ❌ 缺。你给了修法，但没给「怎么证明修好了」 |

**为什么 commit hash 最关键：** 审计报告描述的是**某一个特定版本**的代码。没有 commit hash，
半年后客户拿着改过的代码来问「你说的问题还在吗」，你是无法回答的。这是个专业性硬门槛。

## 4. 文字与排版

### 4.1 拼写错误一览

| 行 | 原文 | 应为 |
| --- | --- | --- |
| 1 | `protocal` | `protocol` |
| 6 | `Varibles` | `Variables` |
| 6 | `parvite` | `private` |
| 11 | `vosable` | `visible` |
| 11 | `on/-chain` | `on-chain` |
| 11 | `varible` | `variable` |
| 11 | `asscessed` | `accessed` |
| 17 | `竞技审计` | 应为 `竞赛审计`（competitive audit）—— 这是术语错误，不是笔误 |
| 20 | `Creat` | `Create` |
| 31 | `beacuse` | `because` |
| 33 | `rcp-url` | `rpc-url` |
| 53 | `protocal`（再次） | `protocol` |
| 66 | `assess controls` | `access control` |
| 66 | `$>>` | 删除（复制粘贴残留） |
| 71 | `severly` | `severely` |
| 104/116 | `PassWordStore` | `PasswordStore` |
| 112 | `their is` | `there is` |
| 112 | `funtion` | `function` |
| 116 | `getPassWord` | `getPassword` |

> 值得注意的模式：错误集中在**手速快于拼写检查**的地方（`visable` / `vosable` / `asscessed` 三种拼法
> 出现在同一句里）。`PassWordStore` 与 `getPassWord` 这两个错误尤其要警惕 —— 它们是**标识符**，
> 拼错意味着「没对着源码抄」。建议：所有出现的函数名、变量名、事件名，写完后再去源码里 `Ctrl+F` 一遍。

### 4.2 标点与大小写

- **逗号前加空格**：`:6` `to anyone , no matter`、`:62`（应为 `,` 后加空格处反而没加）等。
  英文写作中逗号前不加空格、逗号后加空格 —— 你的问题是**两者都反了**。
- `:119` `**Impact:** The natspec is incorrect.` —— `natspec` 应为 `NatSpec`（专有名词，大小写固定）。
- 函数名、变量名应使用反引号包裹：`:62` 的 `setPassword` 包了，`:71` 的没有。

### 4.3 Markdown 结构问题

**（a）`<details>` 标签未闭合** —— `:75` 开启，`:91` 结束代码块，但**全文没有 `</details>`**。
渲染时从该处起，后面所有内容都会被折叠掉。

**（b）代码块语言标注错误** —— `:64`、`:78`、`:96` 三处均标为 ` ```javascript `，但内容是 Solidity。
**改法：** ` ```solidity `。这不是小事：语言标注决定了渲染器的语法高亮，标错了代码在报告里是灰的，
而审计报告的可读性有很大一部分来自代码高亮。

**（c）缺少 H1 标题** —— 全文最高层级是 `###`。Markdown 文档应当有一个 `#` 开头的文档标题。

**（d）发现未按等级排序后就编号** —— 顺序本身对（High、High、Info），但编号没建立，导致无法交叉引用。

### 4.4 必须删除的草稿残留

这几处是**写给自己看**的，出现在交付稿里会显得不专业：

| 行 | 内容 | 处理 |
| --- | --- | --- |
| 1-3 | `1.Convince the protocal... / 2.How bad... / 3.How to fix...` | 这是写作提纲，删除，或移到正文之外的「写作笔记」文件 |
| 9 | `or clearly:` + 另一个备选标题 | 二选一，删掉另一个 |
| 17 | `//对于竞赛审计 或者面对缺乏经验初级的开发人员团队，在这里提供这些证据` | 内部思考，删除 |
| 39 | `//你可以用下面这个工具把这段十六进制（hex）解析成字符串` | 中文旁注混在英文报告里 —— 见 §4.5 |
| 49 | `（翻译：缓解措施）` | 同上 |
| 55 | `ps：As a security researcher, it's hard to say: hey this protocol should be scrapped...` | **内容很好，但位置错了** —— 这段「给开发者的建议」不该塞在 Mitigation 里，应移到报告的「总结/结语」章节 |

### 4.5 中英混排的处理

`:53`、`:62`、`:94` 等处采用了「英文正文 + `CN：` 接中文翻译」的写法。

作为**学习笔记**，这很好 —— 它是有效的双语训练方式。但作为**交付给客户的报告**，这是不成立的：
客户读英文版或中文版，不会读一份每段都写两遍的文档。

**建议的分离方式：** 保留这份双语笔记（它记录了你的学习过程），把**交付稿**单独写成纯英文或纯中文的一版。
本次我做的两份报告就是这个思路 —— 中文版不是英文版的逐句翻译，而是按中文技术写作习惯重写的一版
（例如「根本原因是缺少调用者校验，而不是 `external` 这个关键字 —— 可见性与授权是两个独立问题」这类
解释性插入，是我按中文读者的理解路径补的，英文版里没有）。

## 5. 工程与仓库规范

### 5.1 直接在受审源码里加批注

你在 `src/PasswordStore.sol` 里直接插入了 `//@audit` 注释和 `//0` `//1` 槽位标记。

**问题：** 审计报告声明的是「某个版本的代码」，而受审源码被就地改动后，那个版本就不存在了 ——
报告与代码库无法互相对照。虽然 `git diff` 能还原，但这是运气，不是方法。

**更好的做法（任选）：**
- 把受审源码原样保留（`git stash` 或另开分支），批注写在独立的 `notes/` 文件里；
- 或者接受改动，但在报告里写清楚「受审版本 = commit `xxxxxxx`，工作区批注不属于受审版本」。
  我在两份报告的开头都加了这一节版本说明（§1.1），就是这个原因。

### 5.2 README 被覆盖 —— 这是一次真实的信息丢失

你仓库当前 `README.md` 是 Foundry 脚手架生成的通用模板（`forge init` 的产物），
**原始 README 被完全覆盖了**。而原 README 里恰好写着本次审计最需要的东西：

```
# Audit Scope Details
- Commit Hash:  2e8f81e263b3a9d18fab4fb5c46805ffc10a9990
- In Scope: ./src/ └── PasswordStore.sol
- Solc Version: 0.8.18
- Chain(s) to deploy contract to: Ethereum
```

也就是说：**§3 表格里说「缺失的审计范围章节」，你其实曾经有过，后来自己弄丢了。**

好消息是它可以从 git 里完整恢复：

```bash
git show 2e8f81e:README.md          # 查看原始版本
git show 2e8f81e:README.md > README.orig.md   # 导出备份
```

**教训：** `forge init` 会覆盖 `README.md`。在任何已经写过内容的仓库里执行它之前，先 `git commit` 或备份。
这也是为什么本次改 README 时，我把原版内容作为附录完整保留了下来（见仓库根目录 README 的
「Appendix — Original project README」一节），而不是直接替换。

### 5.3 目录命名

`audit-date/` —— 从上下文看，本意应是 `audit-data/`（审计数据）或 `audit-notes/`（审计笔记）。
`date`（日期）在这里讲不通。

我没有替你改（你说了不要动手写版，我也不想擅自移动你的目录）。但建议你**在推送到作品集之前**改名 ——
招聘方看到作品集里第一个目录名就拼错，印象分是负的。

```bash
git mv audit-date audit-notes
```

### 5.4 `.gitignore` 与构建产物

当前 `out/`、`cache/` 已被 `.gitignore` 忽略（正确）。但 `broadcast/` 需注意：
`.gitignore` 里只忽略了 `broadcast/*/31337/` 和 `broadcast/**/dry-run/`，
本地的部署记录（含交易哈希）会被提交进去。对作品集而言这无伤大雅，甚至能佐证「你真的部署跑过」，
但如果将来接入真实链，`broadcast/` 里可能含 RPC 端点等信息，届时要一并处理 `.env`。

## 6. 作为「作品集」的定位建议

你现在要把它当作品集提交，这里有一个**真实的张力**需要你自己决定怎么处理：

> 这份报告发现的问题「很少、很简单」，而这**不是你的水平问题** —— `PasswordStore` 本身就是 Cyfrin
> 课程设计的教学靶场，它的漏洞是刻意埋的、且只有 47 行代码。

所以作品集真正要展示的**不是「我发现了什么」，而是「我怎么做的」**。基于这一点，建议：

**要突出的：**
1. **PoC 是真跑出来的。** 那段十六进制你亲手复现过 —— 这一点比报告的辞藻重要得多。
2. **区分「能打补丁的」和「必须改架构的」。** 手写版第 1 条最后那句
   *"As a security researcher, it's hard to say: hey this protocol should be scrapped"* 触及了一个
   真正专业的判断：**H-1 不是代码 bug，是需求本身在透明账本上无法满足**。这个洞察很值钱，
   但你没有把它提炼出来 —— 它被埋在 Mitigation 段的 `ps:` 里了。我把它提到了两份报告的「结语」章节。
3. **如实标注 AI 生成。** 你已经这么要求了，而且我认为这是对的：一个主动披露 AI 参与、并且
   **同时给出「AI 报告的短板是什么」**（未见客户、未经复评）的作者，比一个假装全是自己写的人可信得多。

**要避免的：**
- 不要因为「只有 3 条」就硬凑到 20 条。等级诚实的 9 条远胜于灌水的 20 条。
- 不要在报告里保留「内部思考」的痕迹（`ps：`、`//` 中文旁注、`or clearly:`），
  这些应该留在笔记版里 —— 而笔记版**本身也是有价值的作品**，它展示了你的学习过程。
